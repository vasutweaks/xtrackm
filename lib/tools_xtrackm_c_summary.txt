1. MAIN FUNCTION
--------------------------------------------------------------------------------

    track_dist_time_asn_midx(ds, var_str="sla", units_in="m", dist_from="track")

Returns an (x, time) DataArray in which lat and lon carry their own xarray
indexes, so all three access patterns work on the same object:

    da = track_dist_time_asn_midx(ds, "sla", units_in="km")
    da.sel(x=slice(0, 200))             # along distance from coast
    da.sel(time=slice("2005", "2010"))  # along time
    da.sel(lat=15.0, method="nearest")  # along latitude
    da.sel(lon=95.0, method="nearest")  # along longitude

It also handles 1-D variables (mssh, mdt) -- they come back as (x,) -- which
collapses track_dist_asn_mssh and track_dist_asn_mdt into the same call.

Axes produced:
    x     along-track distance from the coast, increasing offshore
    time  one time stamp per cycle
    lat   latitude of each along-track point   (indexed, so .sel works)
    lon   longitude of each along-track point  (indexed, so .sel works)

Extra coordinates carried along: points_numbers (on x), cycles_numbers (on time).


--------------------------------------------------------------------------------
2. SUPPORTING FUNCTIONS
--------------------------------------------------------------------------------

    along_track_dist(ds, units_in="m", dist_from="track")
        Distance to the coast for every track point, in file (equator->coast)
        order.
        dist_from="track"  geodesic distance to the coastal end point
        dist_from="gshhg"  the dist_to_coast_gshhg variable in the file

    track_time(ds)
        One datetime64 stamp per cycle, as a pandas DatetimeIndex.
        Median of the valid point times; empty cycles filled by linear
        interpolation against cycle number.

    sel_track(da, x=None, lat=None, lon=None, time=None, method="nearest")
        Select along distance, latitude, longitude and/or time in one call.
        Each argument takes a scalar (nearest point) or a (lo, hi) pair
        (inclusive range, given in natural order regardless of how the
        coordinate runs along the track).

            sel_track(da, x=(0, 200))                    # 0-200 km from coast
            sel_track(da, lat=12.5)                      # nearest point
            sel_track(da, lat=(10, 20), time=("2005", "2010"))


--------------------------------------------------------------------------------
3. WHAT CHANGED VERSUS THE OLD VERSION
--------------------------------------------------------------------------------

DISTANCE
    Now uses pyproj.Geod.inv instead of a Python loop over geopy.distance.
    Same Karney (2013) geodesic the draft cites, agreeing to 2e-13 km, but
    vectorized.

TIME
    No longer truncated to whole days. The old timedelta(days=int(d)) threw
    away up to 23.9 h per cycle; the new version keeps sub-second precision and
    takes the median over valid points rather than trusting the mid-track
    point. Empty cycles are filled by interpolation against cycle number
    instead of ffill/bfill, which would have produced duplicate stamps in the
    index.

DECODE_TIMES
    Works either way. The old function crashed on a decoded dataset
    (int() on a cftime.DatetimeJulian); both paths now give identical times to
    within 6e-7 s.

GSHHG OPTION
    dist_from="gshhg" folds in what track_dist_time_asn_gshhg did.
    NOTE: dist_to_coast_gshhg is distance to the *nearest* coastline, so it is
    not monotonic along the track -- with that option x is not sorted and
    slicing on it will not behave. The "track" default is the s defined in the
    draft's methods section.

FUNCTIONS COLLAPSED INTO ONE
    track_dist_time_asn         -> track_dist_time_asn_midx
    track_dist_time_asn_gshhg   -> ... dist_from="gshhg"
    track_dist_time_asn_midx    -> (this function)
    track_dist_asn_mssh         -> ... var_str="mssh"  (returns (x,))
    track_dist_asn_mdt          -> ... var_str="mdt"   (returns (x,))
    dist_asn_gshhg              -> along_track_dist(..., dist_from="gshhg")

--------------------------------------------------------------------------------
5. BACKGROUND FROM THE DRAFT (Data and Methods)
--------------------------------------------------------------------------------

X-TRACK L2P v2.2 files store every variable on (points_numbers,
cycles_numbers), with the first point on the equator and the last point on the
coast. The draft states the variables are reshaped as a function of distance
(s) from the coast and time, where s is the along-track distance between the
coastal point and the track points on an ellipsoidal model of the earth,
computed with geodesic algorithms (Karney, 2013). That is exactly what x is in
this module.

Time units in the files: "days since 1950-1-1", calendar "julian".
Along-track spatial resolution: 6-7 km (1 Hz sampling).

7. FIXED local_angle / track_angle_at  (in tools_xtrackm_c.py)
--------------------------------------------------------------------------------

The old lib/tools_xtrackm.py local_angle had two problems.

(a) FLAT-EARTH ANGLE.  It used atan2(dlat, dlon), which ignores the convergence
    of the meridians (a degree of longitude is cos(lat) times shorter than a
    degree of latitude). Measured against true geodesic azimuths over all 1421
    tracks: mean error 0.26 deg, p95 0.91 deg, max 2.03 deg, growing with
    latitude (0.08 deg at 0-5N, 1.08 deg at 20-26N). It stays small only
    because these are near-polar orbits -- all headings lie in 13-115 deg, and
    the error vanishes for a purely meridional track.

(b) INDEX-ORDER MISMATCH AT THE CALL SITES -- the larger error.
    index_at_lat / index_at_lon / index_at_x return an index into the REVERSED
    (coast-first) array, but every call site passed it together with the
    FORWARD (equator-first) ds.lon.values / ds.lat.values, so the heading was
    computed at the mirror-image point on the track. Across all tracks the
    latitude actually used was off by mean 9.8 deg (max 25.1 deg), giving an
    alpha error of mean 0.78 deg, p95 2.26 deg, >5 deg in 0.1% of cases (up to
    53 deg on the long GFO tracks spanning 0.16N-19.89N).
    Affected: eicc/p.guv_at_155_116.intersection.S6A.py,
    eicc/p.speed_at_coastal_points.eicc.trends.py,
    eicc/p.along_shore_at_coastal_points.eicc.py,
    eicc/p.guv_at_AtoG.points.S6A_periodogram.py, and the archive/ copies.

THE REPLACEMENTS

    local_angle(lons, lats, ii, ioff=3, degrees=False)
        True geodesic azimuth (Karney 2013) across a centred 2*ioff stencil,
        averaged between the two ends so it refers to ii rather than to the
        start of the stencil. Heading points in the direction of INCREASING
        INDEX -- reversing the arrays rotates the answer by 180 deg.
        Returns NaN (not a silent 0.0) for a degenerate stencil: fewer than two
        points, ii out of range, coincident end points, or a NaN at ii or at
        either end.

    track_angle_at(ds, lat=None, lon=None, x=None, units_in="m", ioff=3,
                   degrees=False, order="file")
        Give exactly one of lat, lon or x (distance from coast). Resolves the
        index and computes the heading in the SAME array order, so the (b) bug
        cannot be reproduced. Returns (angle, ii) with ii in file order.
        order="file"  equator -> coast heading (default; what
                      geostrophic_components expects)
        order="coast" coast -> offshore heading, aligned with the x axis of
                      track_dist_time_asn_midx

STILL OPEN -- SIGN CONVENTIONS IN tools_xtrackm.py vs THE DRAFT
  Two deviations that happen to cancel, so the chain gives the right answer but
  the paper does not describe the code:
    - compute_geostrophy_gc returns +(g/f) dh/ds, not the draft's -(g/f) dh/ds.
      Verified: code gc = +0.4272 where the draft's -u sin a + v cos a gives
      -0.4271 -- equal and opposite.
    - geostrophic_components divides u by sin(a1-a2); the draft has
      sin(a2-a1). v matches the draft.
  Applying the draft's formulas literally to the code's gc gives u with the
  wrong sign. Neither has been changed.
  Minor: the assert a1_r < 3 in geostrophic_components never fires on real data
  (headings are 13-115 deg) but would reject a valid heading above 172 deg, and
  will not catch degrees that happen to be below 3.

================================================================================
8. ISSUES IN THE GEOSTROPHIC CURRENT COMPUTATION
   (investigated 2026-09-09; replacements written in tools_xtrackm_c.py)
================================================================================

HEADLINE: the pipeline is CORRECT, but by accident -- compute_geostrophy_gc and
geostrophic_components each carry a sign error and the two cancel exactly.
Fixing either one alone flips the answer. Separately, the draft's own v formula
IS wrong, which is almost certainly the "[x] meridional component sign issue"
in Issues.txt and the reason gv correlates poorly with AVISO.

--------------------------------------------------------------------------------
8.1  THE TWO CANCELLING SIGN ERRORS
--------------------------------------------------------------------------------
Let alpha be the heading in the direction of increasing x (offshore). Then
    gc = -u sin(alpha) + v cos(alpha) = +(g/f) dh/dx
and the exact inverse at a crossing is
    u = (gc1 cos a2 - gc2 cos a1) / sin(a2 - a1)
    v = (gc1 sin a2 - gc2 sin a1) / sin(a2 - a1)

  - compute_geostrophy_gc returns +(g/f) dh/dx but is used with alpha taken in
    the OPPOSITE (equator -> coast) direction, so its gc is the negative of the
    gc that alpha convention implies.
  - geostrophic_components writes the determinant as sin(a1 - a2) instead of
    sin(a2 - a1), negating BOTH u and v.
  Product of the two: +1. Verified end to end (below).

--------------------------------------------------------------------------------
8.2  THE DRAFT'S v FORMULA IS WRONG
--------------------------------------------------------------------------------
draft_v02.2a.pdf writes
    v = (gc2 sin a1 - gc1 sin a2) / sin(a2 - a1)
The exact inverse of the draft's OWN gc1/gc2 equations is
    v = (gc1 sin a2 - gc2 sin a1) / sin(a2 - a1)      <- numerator negated
Numerical check, inverting the draft's own projection equations over 18039
random (u, v, a1, a2):
    draft u    recovers the truth in 100.00% of cases
    draft v    recovers the truth in   0.00% of cases
    correct u  100.00%      correct v  100.00%
The draft's gc = -(g/f) dh/ds IS self-consistent with its projection equation,
provided alpha there means the equator -> coast heading (opposite to s). Only
the v inversion is in error. THE PAPER NEEDS THIS FIXED.

--------------------------------------------------------------------------------
8.3  OTHER DEFECTS FOUND
--------------------------------------------------------------------------------
(a) EQUATOR MASK IS ONE-SIDED AND TOO NARROW.
    compute_geostrophy_gc uses np.where(lats > 2, f, nan) -- a one-sided test,
    not |lat| < 2, and its own comment says "2s-2n" while the draft says 5S-5N.
    Harmless only because no NINDIAN track reaches the southern hemisphere
    (checked: 0 of 1418). Between 2N and 5N the median |gc| on GFO 008 is still
    ~1 m/s against ~0.3 m/s further north, so the old mask leaves a
    contaminated band in. New default: symmetric equator_band=5.0.

(b) f AND g ALIGNED BY ARRAY POSITION, NOT BY COORDINATE.
    ratio1 = (g/f)[:, newaxis] built from ds.lat.values[::-1] is multiplied into
    sla_smooth, so the result is silently wrong if sla_smooth was subset,
    sorted, or transposed. The new function reads lat off the DataArray's own
    coordinate.

(c) NO UNIT CHECK ON THE x AXIS.
    gc = (g/f) dh/dx assumes x in metres. Handing it a track built with
    units_in="km" gives currents 1000x too large, silently: measured gc
    +427.2 m/s vs +0.42725 m/s. The new function converts from
    da.x.attrs["units"].

(d) differentiate("x") STRADDLES DATA GAPS.
    Adjacent 1 Hz points are 6-7 km apart, but 0.2% of intervals are gaps up to
    ~1384 km, across which a long-baseline average slope is reported as a local
    gradient. New optional max_gap masks those.

(e) NEAR-PARALLEL THRESHOLD FAR TOO LOOSE.
    geostrophic_components rejects only |sin(a2-a1)| < 1e-6, i.e. crossings
    down to 6e-5 deg, where the inversion is pure noise. New default
    min_sin=0.1 (about 5.7 deg). Its ValueError message is also a broken
    f-string that prints "{math.degrees(theta):.2f}" literally.

(f) assert a1_r < 3 CHECKS ONLY AN UPPER BOUND.
    Will not catch degrees below 3, would reject a valid heading above 172 deg,
    and vanishes under python -O. Replaced by an explicit finite/range check.

(g) OPERATOR PRECEDENCE BUG in geostrophic_current_components_1:
        u = (gd + ga.interp(...)) / 2*cos_theta
    is (x/2)*cos(theta), not x/(2 cos theta) -- 1.333x off at theta=30 deg.
    Same on the v line with sin_theta. This function appears unused; not
    ported.

(h) compute_geostrophy_from_slope uses a single endpoint-to-endpoint slope
    instead of the local heading, and abs(angle), which destroys the sign for
    descending tracks. It also carries a -1 that compute_geostrophy_gc does
    not. Not ported.

(i) NOT A GEOSTROPHY BUG, BUT BLOCKING: track_smooth_loess_x -- the project's
    primary smoother -- crashes with
        numpy.linalg.LinAlgError: SVD did not converge in Linear Least Squares
    on data/GFO/ctoh.sla.ref.GFO.nindian.008.nc. 31 of 186 cycles are entirely
    empty; interpolate_na cannot fill an all-NaN column, so loess_1d is handed
    all-NaN. Needs a guard that skips or NaN-fills empty cycles.

(j) SEPARATE FROM GEOSTROPHY: compute_dist measures from lons_track[-1],
    assuming the LAST point is the coastal one. For 32 unique tracks (64 files
    counting the _lon_ordered links) the FIRST point is nearer the coast, e.g.
    ERS1+ERS2+ENV+SRL/666: first point 7.4 km from a coast, last 105.6 km. The
    x axis is still a valid monotone along-track coordinate, so gc is
    unaffected, but "distance from coast" is measured from the wrong end for
    those tracks -- which corrupts the coastal binning, the EICC transects, and
    the std-vs-distance comparison in the draft.

(the +0.0022 / -0.0049 residual is the old local_angle flat-earth error, section 7)

some scripts but not others.

================================================================================
9. SMOOTHING AND OUTLIER REJECTION -- YES, THESE NEEDED REWRITING
   (investigated 2026-09-09; replacements in tools_xtrackm_c.py)
================================================================================

Every smoother in tools_xtrackm.py either invents data or destroys it, and the
two most-used filters (mad_filter_1d_xr, 31 call sites; butter_lowpass_1d, 20)
are quantitatively wrong. Measured on GFO pass 008 (28695 finite of 39060).

--------------------------------------------------------------------------------
9.1  mad_filter_1d_xr / mad_filter_2d_xr -- 0.6745x TOO LENIENT
--------------------------------------------------------------------------------
        mad = median_abs_deviation(valid_data, scale='normal')
        modified_z_scores = 0.6745 * (da_vals - median) / mad
scale='normal' ALREADY divides by 0.6745, so it returns a robust sigma. The
extra 0.6745 makes every z-score 0.6745x too small:
    std of z as coded            0.6769   (should be 1.0)
    nominal thresh 3.5 cuts at   5.19 sigma
    on Gaussian noise, thresh=3.0 flags 0.000% where it should flag 0.315%
On real data (GFO 008, dim="time"):
    thresh=3.0 : new flags 110 outliers, old flags   2
    thresh=3.5 : new flags  31 outliers, old flags   0
So the project's outlier rejection has been very nearly a no-op. 31 call sites.
mad_filter_1d_xr additionally rebuilds the output with only `dim` as a
coordinate, dropping lat/lon and attrs, and only handles 1-D input.

--------------------------------------------------------------------------------
9.2  butter_lowpass_1d / butter_lowpass_2d -- WRONG SAMPLING RATE
--------------------------------------------------------------------------------
Both hardcode "fs = 1  # Sampling frequency: 1 sample per day". An along-track
series is one sample per satellite REPEAT CYCLE, so a nominal 3-day cutoff is
really 3 cycles, and the physical cutoff changes with the mission:
    TP+J1+J2+J3+S6A / TPN+...   10 d repeat ->  30 days
    HY2A / HY2B                 14 d        ->  42 days
    GFO                         17 d        ->  51 days
    S3A / S3B                   27 d        ->  81 days
    ERS1+ERS2+ENV+SRL           35 d        -> 105 days
Cross-mission comparisons were therefore low-passed at 30-105 days while all
being labelled "3 days". 20 call sites. butter_lowpass_1d silently returns
UNFILTERED data when len <= 15; butter_lowpass_2d lacks that guard and raises
instead.

--------------------------------------------------------------------------------
9.3  THE LOESS SMOOTHERS FABRICATE DATA
--------------------------------------------------------------------------------
Both call
    interpolate_na(dim="x", method="linear", fill_value="extrapolate")
and then keep the result everywhere, so the output has MORE finite values than
the input. track_smooth_loess_statsmodels_x (the primary smoother, used by
computed/c.loess_0.05_smooth.all.py) on GFO 008:
    input  28695 finite  ->  output 32550 finite   = 3855 values invented
    at x = 0 km (the coastal point) 37 valid cycles became 155
Worse, the fabricated points also CORRUPT THE FIT AT GENUINE OBSERVATIONS:
    |new - old| at the 28695 real points: median 0.20 cm, p95 1.3 cm, max 86 cm
    by band: 0-50 km 0.06 cm | 50-150 km 0.61 cm | 150-1600 km 0.19 cm
The 50-150 km transition band -- where the gaps are worst and the paper's
coastal argument lives -- is the most affected.

track_smooth_loess_x additionally RAISES on that same file:
    numpy.linalg.LinAlgError: SVD did not converge in Linear Least Squares
because 31 of 186 cycles are entirely empty, interpolate_na cannot fill an
all-NaN column, and loess_1d is handed all-NaN.

--------------------------------------------------------------------------------
9.4  THE OTHER SMOOTHERS
--------------------------------------------------------------------------------
(a) track_smooth_gaussian_x DESTROYS 59% OF THE DATA. gaussian_filter1d blanks
    the whole kernel footprint around every NaN: 28695 valid points in, 11865
    out. Fixed by normalised convolution (filter the data and a validity mask
    separately, then divide).
(b) track_smooth_box_x DEFAULTS TO smooth=1, a no-op -- calling it without an
    explicit window returns the data unsmoothed. Its min_periods=1 also emits a
    "mean" computed from a single sample.
(c) slope_smooth_optimal_filter_x uses np.convolve, which REVERSES the kernel.
    genweights(-5, 6) is asymmetric, so the applied window is the mirror image
    of the intended one (on a ramp of slope 3: convolve 298.7 vs correlate
    301.3). np.convolve also propagates NaN across the full window (-31% of
    points). Not ported -- it is used only by computed/c.optim_smooth.all.py.
    NOTE: genweights itself is fine; its weights sum to +1 and it is correctly
    applied to an already-differentiated slope field, so the earlier concern
    that it was a derivative kernel misapplied as a smoother does not hold.
(d) None of the smoothers use the physical x spacing -- sigma and window are in
    samples, and LOESS frac is a fraction of points, so the effective physical
    scale varies across the gaps documented in section 8.3(d).

--------------------------------------------------------------------------------
9.5  NEW FUNCTIONS
--------------------------------------------------------------------------------
Two rules, applied uniformly:
  1. never invent data -- a NaN on input stays NaN on output unless the caller
     explicitly asks, via a named argument, for gaps up to a stated width;
  2. never silently destroy it -- one NaN in a kernel must not blank the window.

    mad_filter(da, thresh=3.5, dim=None)
        correct modified z-score; any number of dimensions; dim may be a tuple
        to filter along each in turn (what mad_filter_2d_xr did); keeps every
        coordinate and attribute
    smooth_box(da, window=6, min_count=None, dim="x", keep_coverage=True)
        min_count defaults to half the window
    smooth_gaussian(da, sigma=3, dim="x", min_weight=0.5, keep_coverage=True)
        normalised convolution; min_weight drops points with too little real
        kernel support
    smooth_loess(da, frac=0.05, dim="x", min_points=10, fill_gaps=None)
        fits on finite samples only; series shorter than min_points return NaN
        instead of raising; fill_gaps (in x units) is the explicit opt-in for
        bounded gap filling
    lowpass_time(da, cutoff_days, order=4, dim="time")
        sampling interval taken from the time coordinate itself, so the mission
        no longer has to be known; a cutoff at or below the Nyquist period is
        refused rather than silently meaningless; records sampling_days and
        lowpass_cutoff_days in the output attrs
